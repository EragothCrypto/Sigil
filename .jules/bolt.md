## 2025-02-12 - Prevented O(N) array filtering and O(N) component re-renders
**Learning:** In React, array indexes as keys break the `React.memo` optimization if elements are hidden/filtered dynamically. If unchanged entries are hidden, and array index `i` is used as a `key`, React will shift the keys causing unchanged components to re-render, effectively defeating `React.memo` for the remaining elements and causing bugs with any local state (like open/closed).
**Action:** Use a unique, stable identifier like `key={`${entry.status}-${entry.fn.signature}`}` instead of `i`. Memoize derived arrays using `useMemo` so that the component does not perform O(N) filtering on every render.
## 2024-06-25 - React Component Re-render Bottleneck in Text Parsing
**Learning:** React components that parse strings recursively and dynamically create regex objects (e.g., in a loop over a large dictionary like `JARGON_GLOSSARY`) can cause severe O(N*M) performance bottlenecks during parsing, especially when not memoized, causing the expensive recursive work to trigger on every re-render.
**Action:** Always extract sorting and RegExp instantiation for static dictionaries to the module level (precompilation), and use `memo`/`useMemo` to prevent deep recalculations when the source text does not change.
## 2024-07-28 - Chained Array Operations Overhead
**Learning:** Repeated array method chaining (e.g., `.filter().length`, `.reduce()`, `.map()`) on the same dataset in reporting functions creates O(K*N) passes over the data. In `buildWalletMonitorReport`, the dataset was traversed 16 times in succession, causing noticeable CPU overhead as the watchlist size grows.
**Action:** Replace multiple chained array passes with a single `for` loop that accumulates all necessary counters, metrics, and conditional logic in one O(N) pass.
## 2025-02-12 - Reaffirmed Pattern of Chained Array Overheads
**Learning:** The anti-pattern of using multiple `.filter(..).length` and `.reduce(..)` chaining was identified again in `approval-health.ts`/`approvals.ts`, leading to 4x O(N) passes over potentially large arrays of logs/approvals. This confirms that this API-tier overhead remains a common risk throughout this codebase.
**Action:** Always replace multiple chained array passes over the same list with a single accumulator loop `for (let i = 0; i < approvals.length; i++) { ... }` when deriving multiple aggregate metrics from an array.
## 2024-03-24 - Batch Etherscan API calls for contract reputation
**Learning:** Etherscan limits to 5 req/sec on the free tier. Making concurrent API calls per item using `Promise.allSettled` uses more network overhead and quota than necessary when we can retrieve up to 200 items in a single paginated Etherscan API call using offset 200.
**Action:** When querying Etherscan, always max out the offset limit (up to 200) instead of concurrently firing requests when trying to get a large number of items. Also gracefully handle rejection/error conditions using `.catch(() => ({}))` to maintain fault tolerance instead of just directly awaiting.
## 2025-02-12 - Drizzle JSONB Filtering in API tier vs DB
**Learning:** In the API server, Drizzle ORM was used to fetch a large number of records (`limit(200)`), after which an in-memory `.filter()` was used to check values inside a JSONB column (`details`). This is highly inefficient because it fetches unnecessary rows from PostgreSQL, creates heavy memory pressure on the Node process, and risks missing data if the target record sits at position 201.
**Action:** Push filtering logic down to PostgreSQL. Use Drizzle's `sql` tagged template literal (e.g. `sql\`${table.details}->>'key' = ${value}\``) to filter on JSONB keys directly inside the `where` clause, avoiding full table scans and memory bloat.
